# Normalisation: from raw SeatGeek data to 3NF

**Project:** SmartTicket · **Student:** FUMBA Huriro (25401) · **Phase:** II, Data Sourcing, Normalisation and Logical Design

All rows below are **real rows** from `data/raw/`, mainly from event **18413002, "Los Angeles Lakers at New Orleans Pelicans"** at the Smoothie King Center. Surrogate keys such as `section_id` and `ticket_id` do not exist in the raw data. They are shown as `S1`, `T1` and so on, and will be generated by Oracle identity columns in Phase IV.

---

## 1. Entities found in the raw data

| Raw structure | What it is | Becomes |
|---|---|---|
| `venues.csv` row | A nested venue object referenced by every event | `VENUES` |
| `listings.section` + `sectionFull`, repeated in thousands of listings | A **repeated value** that belongs to a venue | `SECTIONS` |
| `events.type` / `taxonomyName` / `taxonomySubName` and the same fields in `performers` | **Repeated values** forming a hierarchy (sports → basketball → nba) | `CATEGORIES` (self-referencing) |
| `performers.csv` row | Team or artist | `PERFORMERS` |
| `events.csv` row (33 repeated snapshot rows removed) | Event | `EVENTS` |
| `events.performerIds = [2116,2110]` | A **list** inside an event, and a many-to-many link (one event has many performers; one performer plays many events) | Junction table `EVENT_PERFORMERS` |
| `listings.seats = ['4','5','6']` | A **list** of seats inside a listing | Child rows, one `TICKETS` row per seat |

That gives **7 tables from the dataset**. The 9 other tables (`PRICE_TIERS`, `EVENT_PRICES`, `CUSTOMERS`, `BOOKINGS`, `BOOKING_ITEMS`, `PAYMENTS`, `GATE_SCANS`, `PUBLIC_HOLIDAYS`, `AUDIT_LOG`) hold SmartTicket's own business data. They are designed in 3NF from the start (section 6), for **16 tables** in total.

## 4. 2NF: remove partial dependencies

**Dependency removed (seats):** every column except `seat_no` depends on `listing_id` alone, which is only *part* of the key (a *partial dependency*). Those columns move to `LISTING`, and `LISTING_SEAT` keeps only the key.

**Dependency removed (performers):** `event_name` depends only on `event_id`, and `performer_name`, `performer_type`, `taxonomy` and `home_venue_id` depend only on `performer_id`. Both are *partial dependencies* on part of the key `(event_id, performer_id)`, so they move to `EVENT` and `PERFORMER`, and `EVENT_PERFORMER` keeps only the key.

## 5. 3NF: remove transitive dependencies

| Transitive dependency found | Split into |
|---|---|
| `listing_id → event_id → event_name, start_utc, venue_id`: event details depend on the event, not the listing | `EVENTS` |
| `event_id → venue_id → venue_name, city, capacity`: venue details depend on the venue, not the event | `VENUES` |
| `(venue_id, section) → section_full`: a section's name depends on the venue section, not the listing (the same "Section 109" appears in every listing for that section) | `SECTIONS` |
| `type → taxonomy` in both events and performers (`nba → basketball → sports`): the sport depends on the league type, not the event or performer | `CATEGORIES`, with `parent_category_id` holding the hierarchy |

Each sentence above is one split. The resulting 3NF tables, with real rows:

**From LISTING to TICKETS.** After these splits, `LISTING` holds only `listing_id, event_id, section_id, row, delivery_type`. A listing is a **resale bundle**: a reseller's offer of some seats. SmartTicket is the organiser's own box office and sells **seats**, so each `LISTING_SEAT` row joined to its listing becomes one `TICKETS` row, and `listing_id` is not kept. Keeping it would add a new transitive dependency (`ticket → listing → event`). `TICKETS` is in 3NF: every column depends on `ticket_id`, and `(event_id, section_id, row_label, seat_no)` is a second candidate key, declared **UNIQUE**. This is what stops a seat from being sold twice, including the **190 double-listed seats** in the raw data.

### Deliberate design choice: venue address

`VENUES` keeps `city`, `state_region`, `country` and `postal_code` together. In theory `postal_code → city`, but postal codes are missing for 6 venues and are not unique across the 6 countries in the data. SmartTicket also never updates a city on its own. A separate `CITIES` table would add a join and no benefit, so the address is treated as one descriptive attribute group of the venue.

## 6. SmartTicket business tables (designed directly in 3NF)

| Table | Key | Why it is already in 3NF |
|---|---|---|
| `PRICE_TIERS` | `tier_id` | One row per tier (VIP, PREMIUM, SILVER, BRONZE). Code, name and default price all describe the tier. |
| `EVENT_PRICES` | `(event_id, tier_id)` | The price depends on the **whole** key: one event and one tier. This resolves the event ↔ tier many-to-many relationship. |
| `CUSTOMERS` | `customer_id` | Anonymous code, region and registration date describe the customer only. |
| `BOOKINGS` | `booking_id` | Customer, time, hold expiry and status depend on the booking. **The total is not stored**, because it is derivable; `fn_booking_total` computes it. |
| `BOOKING_ITEMS` | `booking_item_id` | One ticket in one booking. `price_paid_rwf` is the price *at the time of sale*, which is a fact about the sale. It is not a copy of `EVENT_PRICES`, which can change later. |
| `PAYMENTS` | `payment_id` | Method, amount, reference and status describe one payment attempt for a booking. |
| `GATE_SCANS` | `scan_id` | One scan of one ticket at one gate and time, with its result. |
| `PUBLIC_HOLIDAYS` | `holiday_date` | The holiday name depends on the date. |
| `AUDIT_LOG` | `audit_id` | One logged action, with who, what, when and result. |

## 8. Changes since the Phase 0 plan

| Phase 0 | Phase II | Why |
|---|---|---|
| 15 tables | **16 tables**: `CATEGORIES` added | `type → taxonomy` is a transitive dependency |
| `BOOKINGS` stores the total | Total **not stored** | Derivable; `fn_booking_total` computes it |
| `BOOKING_ITEMS` UNIQUE `ticket_id` | Not a plain UNIQUE; `trg_no_double_sale` allows a ticket in a new booking only after the earlier booking is cancelled | A plain UNIQUE would stop a released seat from being sold again |
